03DAG aur Agent kya hai

Ye do lafz poore project ki buniyaad hain. Interview mein pakka poochhe jayenge.

Agent kya hai

Simple lafzon mein: agent ek chhota worker hai jo ek kaam karta hai.

Sochо ek restaurant kitchen: ek banda sirf sabzi kaatta hai, doosra sirf pakata hai, teesra sirf plate lagata hai. Har banda apna kaam janta hai. Koi teenon kaam nahi karta.

Hamare project mein har agent ek Python function hai jo state (maujuda halat) leta hai aur apna hissa wapas deta hai. Bas.

DAG kya hai

DAG ka poora naam Directed Acyclic Graph hai. Teen lafz alag alag samjho:

Graph

Boxes aur teer (arrows) ka naqsha. Har box ek kaam, har teer batata hai aage kya hoga.

Directed

Teer sirf ek taraf jate hain. A se B jate ho to B se A wapas nahi aa sakte.

Acyclic

Koi gol chakkar nahi. Kabhi bhi wahin wapas nahi pohanchte jahan se chale the — isliye kabhi infinite loop nahi banta.

Aasan misaal: metro ka naqsha DAG jaisa hai — train aage barhti hai, peeche nahi aati, aur beech mein raaste alag alag mud sakte hain. Lekin ek hi station pe do baar nahi aati.

Hamara DAG

Teen faisle ke mor

  1. Planner ke baad: agar LLM ne koi kaam ka plan nahi diya, to plan_fallback pe chale jao — jahan ek tayyar-shuda simple plan rakha hai.
  2. Retrieval ke baad: kitna data aaya? Aadha se zyada aaya to normal raasta. Thora aaya to partial_data_fallback — lekin jo aaya hai wo phenkte nahi, use karte hain. Kuch nahi aaya to no_data_fallback.
  3. Extraction ke baad: koi record bana? Nahi to no_data_fallback.
Ye bara point hai

Retrieval ek loop nahi hai. LangGraph ka Send use karke har API call apna alag node ban jati hai jo saath saath chalti hai. Faida: har call ka apna time, apni retry count, aur apna failure record hota hai. Ek loop mein ye sab ek hi number mein mil jata aur pata na chalta ke kaunsi call slow thi.

06Interview ke sawal

Pehle khud jawab sochо, phir kholo. Yehi tareeqa yaad rakhne mein madad karta hai.

Agent design

Paanch agent kyun banaye, teen kyun nahi?

Kyunki "data laana" aur "data samajhna" ke failure bilkul alag hain. Retrieval network ki wajah se fail hoti hai aur retry chahti hai. Extraction tab fail hoti hai jab API apni response ki shakal badal de — wahan ek record chhorna chahiye, poora run nahi. Analysis tab fail hoti hai jab LLM ghalat JSON de. Agar teenon ek jagah hon to ek try/except teen alag masloon ko cover karega, aur report mein ye batana namumkin ho jayega ke kaunsa hissa degrade hua.

retrieval_gate to kuch karta hi nahi lagta — ye alag node kyun hai?

Wo do kaam karta hai jo edge nahi kar sakti: success ratio nikalta hai aur usko log aur metrics mein record karta hai. Faisla (routing) edge par hai. Alag rakhne ka faida ye hai ke edge function saaf aur sasta rehta hai — LangGraph usay ek se zyada baar bula sakta hai — jabke measurement sirf ek baar hoti hai. Aur saath saath chalne wale retrieval workers ko kahin to jur na hai, wo join point yehi hai.

Planner LLM use karta hai lekin plan_fallback nahi — ye ulta nahi?

Jaan bujh kar. Fallback ka wajood hi is liye hai ke jab model kaam na kare. Agar wo bhi model ko call karta to wo fallback hota hi nahi. Wo jaan bujh kar simple hai — profile se teen seed queries. Uska maqsad planner ki aqal ki naqal karna nahi, balke kuch na dene ke bajaye ek asli report dena hai.

DAG aur LangGraph

LangGraph kyun, seedha functions kyun nahi?

Sach ye hai ke is size pe functions se bhi kaam chal jata. LangGraph teen jagah faida deta hai: Send se parallel fan-out aur khud-ba-khud join; conditional edges structure ki tarah declare hoti hain na ke code mein chhupi if statements; aur state reducers. Teesri cheez hi wo hai jo khud likhne pe ghalat ho jati hai — parallel branches ka data merge karna dekhne mein aasan lagta hai lekin race condition ban jata hai.

Ye waqai DAG hai? Tumhare paas to fallback nodes hain.

Haan — har edge aage jati hai. partial_data_fallback extraction ko jati hai, extraction analysis ya terminal fallback ko, aur dono report pe khatam hote hain. Koi edge peeche nahi jati. Ye maine jaan bujh kar rakha: agla natural feature ek plan→retrieve→replan loop hai, aur wahan ye DAG nahi rahega — us waqt ek explicit iteration limit lagani paregi.

Do parallel branches ek hi state key pe likh dein to?

Bina reducer ke aakhri wali jeet jayegi aur data chup chaap gum ho jayega. Isliye invocations, retrieval_errors aur node_path par operator.add reducer laga hai, aur flags par dict-merge. Jin keys ko sirf ek node likhta hai — jaise records, insights — unhein reducer ki zaroorat nahi.

Send kya hai aur kyun use kiya?

Send LangGraph ka tareeqa hai jisse ek conditional edge kai branches bana sakti hai. Planner 6 calls banata hai to 6 alag retrieval_worker node executions banti hain jo saath saath chalti hain.

Faida: har call ka apna time, apni retry count, apna failure record. Agar loop hota to chhe calls ka ek hi timing number milta, aur ek call fail hone se paanch achi calls bhi mar jatin.

Tool calling

LLM ke tool arguments kaise validate karte ho?

Teen marhale. Pehle alias repair — model aksar keyword ki jagah query likh deta hai, ek chhoti table un ginay-chunay synonyms ko theek karti hai. Phir Pydantic validation — extra="forbid" ke saath, taake model ka bana hua faltu field chup chaap ignore na ho balke pakra jaye. Teesra, fail closed — jo call ghalat hai wo ek structured rejection record ban jati hai jismein field-level detail hoti hai, aur baqi plan chalta rehta hai.

Ek giant "call DataForSEO" tool kyun nahi banaya?

Brief ne bhi mana kiya tha, aur wajah wazeh hai: ek hi tool ka matlab hai ke faisla ek free-text argument mein chala jayega jise check karne ke liye koi schema hi nahi. Alag tools ke saath har ek ke apne typed arguments hain, apni description hai jo model ko batati hai kab use karna hai, aur apna circuit breaker hai.

Model ne 50 mahangi calls maang lein to?

MAX_PLANNED_CALLS plan ko kaat deta hai aur har extra call ka reason record karta hai. Tool descriptions bhi batati hain ke batch karo — keyword_search_volume ek call mein 20 keywords leta hai.

Tumne plan mein "coverage top-up" kyun daala? Kya ye kharab model ko chhupana nahi?

Nahi, kyunki wo record hota hai. Live testing mein Groq ka model chahe prompt jaisa bhi ho, ek hi tool call deta tha — aisa plan visibility ka sawal answer hi nahi kar sakta. Top-up sirf un queries ki coverage poori karta hai jo model ne khud chuni; nayi query kabhi nahi banata, aur khali plan pe kabhi nahi chalta (wo ab bhi plan_fallback pe jata hai).

plan_source model+topup ho jata hai aur notes mein likha hota hai kya add hua — to plan ki quality naapi ja sakti hai. Chhupana wo hota agar main run ko patla chhor deta aur unknown ko finding bana ke pesh karta.

DataForSEO

Tumne live API use nahi ki — phir kaise pata chale ye kaam karta hai?

Brief ne mock ko saaf allow kiya tha, isliye committed default mock hai. Live client mukammal hai — Basic auth, alag connect/read timeouts, HTTP status classification, aur response body ke status codes.

Maine credentials verify bhi ki hain: auth pass hoti hai (HTTP 200), aur ek asli SERP call chala ke rankings bhi dekhi hain. Jo abhi bhi cover nahi hua wo production payloads ke real-world edge cases hain — funded account milte hi sabse pehle wahi reconcile karunga.

DataForSEO API mein sabse tricky cheez kya thi?

Wo 200 OK bhejta hai lekin asli failure body mein hoti hai — aur do jagah: ek top-level status_code aur ek har task ka apna. Jo client sirf HTTP status pe bharosa kare wo ek fail hui task ko "khali result" samajh lega aur us query ke liye "not visible" report kar dega jo usne kabhi check hi nahi ki.

_unwrap() dono levels ko HTTP layer wali error taxonomy mein mila deta hai, taake upar sirf ek qism ki exceptions dikhein.

Aur ek cheez live debugging mein mili: non-2xx pe bhi body mein kaam ki baat hoti hai. Mera client pehle sirf HTTP status pe raise kar deta tha aur wo line kho jati thi. Ab [40104] Please verify your account poora message aata hai.

Resilience

Kaunsi errors retry karte ho aur kyun?

Retry: timeouts, connection errors, 408/425/429, saare 5xx, aur DataForSEO ke 40429 aur 5xxxx codes.

Retry nahi: 4xx — including 401/403 — aur DataForSEO ke 401xx/402xx.

Asool ye hai: kya yehi request bina badle kaamyab ho sakti hai? 400 ka matlab mera payload ghalat hai; usay 4 baar bhejna sirf 4 ghalat requests hain.

Backoff samjhao.

uniform(0, min(base × 2^(attempt-1), max_delay)) — exponential, capped, full jitter. Aur agar server Retry-After bheje to wo jeet jata hai.

Full jitter isliye ke fan-out ki wajah se saari calls ek hi lamhe mein jati hain — agar wo saath fail hoon to saath retry karengi. Full jitter unhein sabse zyada phailata hai. Equal jitter ka guaranteed floor yahan kuch nahi deta.

Circuit breaker kab khulta hai, aur har endpoint ka alag kyun?

Ek endpoint pe paanch lagatar failures. Har endpoint ka alag isliye ke DataForSEO ka AI Overview endpoint down hone ka matlab ye nahi ke SERP endpoint bhi down hai — wo alag alag fail hote hain.

Cooldown ke baad ek half-open probe jane deta hai: kaamyab hui to band, fail hui to dobara khul jata hai aur timer reset.

Circuit breaker ka koi bug pakra tumne?

Haan, aur ye achi kahani hai. CircuitOpenError TransientToolError se inherit karta hai, to retry loop usay pakar ke retry_after tak so jata tha — 8 second — sirf usi nateeje pe pohanchne ke liye jo breaker pehle hi de chuka tha. Fast-fail hi breaker ka poora maqsad hai. Theek karne se failure demo 30+ second se 1.8 second pe aa gaya.

Aadhi retrieval fail ho jaye to customer ko kya milta hai?

HTTP 200. Status partial, degraded: true, jo queries mili unke asli scores, jo nahi mileen unka visibility_status: "unknown", aur report par ek caveat jo saaf batata hai kya missing hai.

Ek cheez main kabhi nahi karta: jo query check hi nahi hui usay not_visible nahi likhta. Wo customer ko aisa content likhwa dega jiski shayad zaroorat hi nahi.

LLM down ho jaye, DataForSEO nahi — to?

Teen alag guards. Planner pakar ke plan_fallback pe chala jata hai. Analysis pakar ke mechanical findings bana leta hai — narrative jata hai, ranking nahi. Report pakar ke apni deterministic markdown summary bana leta hai. Ek test jaan bujh kar analysis model ko crash karata hai aur check karta hai ke run phir bhi poora scored table ke saath complete ho.

Observability

Main on-call hoon, customer kehta hai run slow hai. Kya karoge?

Response se run_uuid lo aur GET /api/v1/runs/{run_uuid} maaro. Wahan node-by-node table milta hai: kaunsa node, kitna time, kitni retries, kaunsa tool fail hua. Agar retrieval worker pe retries hain to per-tool api_failures batata hai kaunsa endpoint.

Aur detail chahiye to har log line pe run_id laga hai — ek filter se poora trace mil jata hai, backoff sleeps aur breaker transitions samet.

LangSmith kyun nahi use kiya?

Dono chahiye, aur dono alag sawal ka jawab dete hain. LangSmith prompt aur response level pe batata hai — model ne teen ghalat tool calls dein aur raw output ye tha. Correlation-ID trace system level pe batata hai — node 6 ne 1.2 second backoff mein guzare AI Mode endpoint ke against. Incident ke waqt doosri cheez pehle chahiye hoti hai, aur wo kisi third-party service ke chalne pe depend nahi karti.

Logs mein kya chhupate ho aur kyun?

Password jaisi keys kisi bhi depth pe *** ban jati hain. Lambi strings aur lists kat jati hain, recursion depth-bounded hai. Do wajah: ek raw SERP response ~80 KB ka hota hai aur poora log karne se asli signal dab jata hai; aur logs third-party aggregators pe jate hain — customer ka data wahan pohanchna ek aisa leak hai jo kisi ko nazar nahi aata.

Observability layer mein koi bug mila?

Haan. logging.makeRecord KeyError phenkta hai agar extra mein koi aisa naam ho jo LogRecord ka apna attribute hai — aur message dono cheezein hai: reserved bhi, aur error dict ke liye sabse natural key bhi.

To mera pehla version har rejected tool call pe crash karta tha — bilkul wahi raasta jo graceful hona chahiye tha. Test ne pakra. Fix safe_extra() hai jo takraane wale naamon ko prefix kar deta hai.

Production mein kis cheez pe alert lagate?

DataForSEO error rate 5% se upar 5 minute tak; koi bhi circuit ek minute se zyada khula; p95 run duration; aur partial/failed runs ka ratio.

Aakhri wala wo hai jo log bhool jate hain — wo khamosh quality decay pakarta hai, jahan har run technically kaamyab hota hai lekin data patla se patla hota jata hai.

API aur Database

Run synchronous kyun hai?

Brief ne allow kiya tha aur isse submission focused rahi. Production ke liye ye ghalat hai — 10 se 30 second ki held request load balancer timeout ya deploy nahi jhelti. Sahi shakal hai 202 Accepted + queue + status polling. Seam pehle se theek hai: PipelineService.run_profile ek profile leta hai aur run wapas deta hai, request-scoped kuch bhi chhoota nahi.

Duplicate domain pe 409 kyun, existing profile kyun nahi wapas kiya?

Kyunki collection pe POST ka matlab "banao" hai. Chup chaap purana resource wapas karna client ka bug chhupata hai. Agar upsert chahiye to wo PUT hai domain-keyed URL pe. 409 body mein conflicting domain ke saath client ko theek theek batata hai kya hua.

Recheck ka aisa kya masla tha?

Ye asli bug tha jo maine pakra. Recheck bhi ek "run" hai, to /queries endpoint "latest run" resolve karke recheck pe pohanch jata tha — aur recheck ka apna query set nahi hota. Nateeja: koi bhi recheck karte hi queries aur recommendations dono khali ho jate the.

Fix: recheck trigger="recheck" ke saath record hota hai aur "latest full run" ke muqable mein ginta nahi. Ek regression test bilkul isi cheez ko pin karta hai.

node_executions table kyun banayi jab logs pehle se hain?

Alag retention aur alag query pattern. Logs roll off ho jate hain aur join nahi hote. Table se mahine baad bhi SQL mein poocha ja sakta hai: "wo saare runs dikhao jahan analysis node ne 2 second se zyada liye." Logs detail rakhte hain, table run ki shakal rakhti hai.

Tumhare indexes justify karo.

(profile_uuid, opportunity_score) kyunki /queries profile pe filter karta hai aur score pe descending sort — SQLite plain index se ye sort nahi karega. (run_uuid, visibility_status) kyunki status filter hamesha ek run ke andar chalta hai. Dono composite hain usi tarteeb mein jis mein queries chalti hain.

Scoring

Volume pe log kyun lagaya?

Search volume heavy-tailed hoti hai. 50,000 ke ceiling ke against linear normalization 100-search wali query ko 0.002 deti hai — sifar se farq hi nahi — to ek head term poori ranking pe qabza kar leta hai aur saare long-tail mauqe ghayab ho jate hain. Log space mein wohi query 0.4 se upar aati hai, aur volume double hone ki qeemat har jagah taqreeban barabar rehti hai. +1 volume sifar ke liye hai. Ek test bilkul yehi property check karta hai.

Weights kahan se aaye?

Maine chune, kisi data se fit nahi kiye — isiliye wo constants nahi balke .env mein hain. Visibility gap ko sabse zyada weight is liye ke wo actionability se sabse seedha juda hai. Sahi tareeqa ye hai ke customer ki labelled queries lo aur weights fit karo — yehi mera "golden-set eval harness" wala agla qadam hai.

Score LLM se kyun nahi banwaya?

Teen wajah. Reproducible — wahi data, wahi ranking, har baar. Auditable — customer poochhe ke ye query teesre number pe kyun hai to hisaab dikha sakta hoon. Stable — model upgrade se har customer ka roadmap chup chaap badalna nahi chahiye. LLM wahi karta hai jismein wo acha hai: qualitative narrative.

Visibility boolean kyun nahi, teen states kyun?

Kyunki "humne check kiya aur tum wahan nahi ho" aur "hum check hi nahi kar sake" bilkul alag baatein hain. Inhein milane se customer aisi query pe content likh dega jispe wo pehle se rank kar raha hai. Retrieval degrade ho to wo queries unknown aati hain aur 0.6 gap pe score hoti hain — maani-khez uncertainty, aatm-vishwas ke saath ghalat nahi.

Testing aur scaling

Tumhara sabse qeemti test kaunsa hai?

test_partial_upstream_outage_degrades_but_still_reports. Wo paanch mein se teen endpoints down karta hai aur check karta hai ke run partial raasta le, bache hue data ko phir bhi normalize kare, report phir bhi bane, khud ko degraded mark kare, aur mutasira queries ko not_visible ke bajaye unknown bataye. Chaar alag correctness properties ek saath — aur yehi test wo bug pakarta tha jahan kaamyab retrievals phenki ja rahi thin.

LLM wale pipeline ko deterministic kaise test karte ho?

ScriptedChatModel BaseChatModel implement karta hai aur bilkul wohi shakal wapas deta hai jo asli provider deta hai — usi structure ki tool calls, usi shakal ka JSON. Default mein wo prompt se ek maqool plan bana leta hai taake offline path bhi asli edges chale; tests responses override karke khali plan, ghalat arguments, ya crash force karte hain. Graph ko farq hi nahi parta.

Hazaar profiles, rozana runs — kya badlega?

Runs queue karo — ye blocking cheez hai. SQLite ki jagah Postgres. Circuit breaker state shared (Redis). Response caching normalized tool arguments pe, kyunki us volume pe wohi head terms bar bar maange jate hain aur DataForSEO per task bill karta hai. Aur DataForSEO client pe rate limiting — abhi fan-out utna hi parallel hai jitna plan chaura hai, jo 6 calls pe theek hai aur 600 pe nahi.

Is codebase ka sabse kamzor hissa kya hai?

Extraction agent mein brand-mention detection. Wo substring matching hai — "Surfer SEO" ke liye surferseo.com ke against theek, lekin aise brand ke liye ghalat jiska naam koi aam lafz ho. Aise customers ke liye wo aatm-vishwas ke saath ghalat visibility data banayega, jo bilkul data na banane se bura hai. Kam se kam per-profile alias list chahiye, shayad NER pass. Maine isliye chhora ke brief ke profiles ke liye theek hai, aur main limitation chhupane ke bajaye saaf likhna behtar samajhta hoon.

Mushkil sawal

create_react_agent kyun nahi use kiya, mehnat bach jati?

Kyunki brief ka sabse bara criterion yehi hai ke koi agent data laane aur sochne dono na kare — aur ReAct agent theek wahi ek agent hai jo dono karta hai.

Brief se hat kar bhi: ReAct ke saath main plan paisa kharch hone se pehle dekh nahi sakta, call budget enforce nahi kar sakta, parallel fan-out nahi kar sakta, aur trace ek message list hoti hai na ke node graph. Wo tab sahi tool hai jab agla qadam waqai pichle nateeje pe depend karta ho. Yahan retrieval set pehle se maloom kiya ja sakta hai.

5-7 ghante ke take-home ke liye bohat zyada infrastructure likh di.

Brief ne khud kaha tha ke usay happy path se zyada failure handling aur observability ki fikr hai — to waqt wahan gaya. Jo cheezein extra infrastructure lagti hain — error taxonomy, retry policy, metrics collector — har ek sau line se kam hai, aur wohi failure paths ko testable banati hain. Scoring aur extraction chhote aur seedhe hisse hain.

Kya delete karoge?

related_keyword_ideas sabse kamzor tool hai — planner usay kam hi chunta hai aur uska output sirf analysis ko context deta hai. Aur ToolSpec.cost_weight declare to hai lekin sirf documented hai, enforce nahi. Ya to usay asli budget check mein daloon ya hata doon.

Agar hum tumhe hire karein aur ye Monday ko production jaye, sabse pehle kya theek karoge?

Run ko request thread se hataunga. Baqi sab kuch gracefully degrade karta hai; ek synchronous 30-second endpoint nahi karta — wo load balancer pe fail hota hai, deploy pe fail hota hai, aur safely retry bhi nahi ho sakta kyunki run idempotent nahi. Yehi wo cheez hai jo maujuda design absorb nahi kar sakta.
